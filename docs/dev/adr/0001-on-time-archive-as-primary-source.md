# ADR 0001：主数据源选公交准点存档

> **Status**: Proposed · **Date**: 2026-11-24
>
> 🔴 2026-11-24 更正：状态由 Accepted 改为 Proposed，依据：本决策来自数据源初筛，
> 尚未经过 P0 可行性（[roadmap.md](../roadmap.md)）。P0 通过后改为 Accepted；
> 不通过则按 roadmap 里的出路另写 ADR 取代本篇。

决策：项目的主数据源是 City of Winnipeg 的 Transit On-Time Performance
（存档 `cymk-nyei` + 最近一期 `gp3k-am4u`）。

## 1. 背景

要找一个温尼伯本地、有一定规模、质量可靠的公开数据源，做一个数据工程加机器学习的项目。
条件：

- 本地数据，解决本地问题；
- 量足够大，数据工程有实际工作量；
- 有一个能直接测量的目标变量，不需要自己构造评分；
- 能做成面向用户的应用，而不只是一条分析管道。

## 2. 决策依据

准点存档在四条上都满足（数字见 [data-sources.md](../requirements/data-sources.md)）：

- 约 6.25 亿行，2017-07 至今，单月 80 到 204 MB 压缩包，回填本身就是工程问题；
- 目标变量直接在数据里：每班车在每一站的偏差秒数；
- 能和 GTFS 时刻表联结还原班次（D19 抽样一天全部匹配），可以落到“单个班次”这个
  用户认得出的单位上；
- 有明确的使用者（乘客）和使用场景（前一天规划出行）。

## 3. 被否决的方案

比较时依据 2026-11-24 门户上的 `count(*)` 和字段。

- **自行车固定计数站** `rgun-mmqs`：4,309,224 行，2016 年起，26 个站点。
  只有站点、时间、计数、坐标五个字段，没有方向；按月更新、滞后约两个月；
  有整月缺失（The Forks 站 2026-01）和可疑突增（同站 2025-01 约为次月的 2.4 倍）；
  一半站点是 2021 年以后新装的。能做的目标（骑行量预测、计数器故障检测）撑不起应用。
- **消防急救呼叫记录** `yg42-q284`：1,377,678 行，2015 年起，每天更新。
  业务故事直接，但使用者是运营方而不是公众，做不成面向用户的应用。保留为备选。
- **停车罚单** `bhrt-29rb`：1,905,987 行，2010 年起。目标（罚单热点）对公众价值有限。
- **市议会投票记录和会议文本** `f9mn-vti8` 等：120,987 行投票记录。适合文本和检索方向，
  与本项目的数据工程加预测定位不符。
- **311 服务请求**：量大，但同一批数据已在冬季运营类的其他项目里用过，重复度高。
- 另有河流洪峰、农业产量、电力负荷等方向在更早阶段被列为候选，本次比较没有展开。

## 4. 后果

- 项目从第一天起依赖 GTFS 时刻表来还原班次，历史各期 GTFS 的可得性变成承重条件。
- 缺班（一天 114 班里只有 37 班有记录）成为第一风险，P0 先查，
  见 [roadmap.md](../roadmap.md)。
- 2025 年线网改造把数据切成前后两段，建模要分开处理线路身份和外部因素效应。
