# ADR 0003：特征只用前一天已知的信息，311 不进 v1

> **Status**: Accepted · **Date**: 2026-11-24

决策：v1 的每个特征都必须在预测时点（服务日前一天晚上）可知。训练时也按这条规则
构造特征，不使用当天才发生的观测。311 服务请求不进 v1。

## 1. 背景

产品在前一天给出概率（[ADR 0002](0002-trip-reliability-not-realtime-eta.md)）。
如果训练时用了当天才知道的信息（当天实测降雪、当天的投诉量、当天的实时路况），
离线评估会好看，上线后却拿不到这些输入，模型表现会断崖式下降。

## 2. 决策

特征分三类处理：

- **前一天可知**：天气预报、已公布的停车禁令和车道封闭、日历、固定的道路和站点属性、
  历史统计（截至前一天）。v1 直接用。
- **只有事后观测**：当天实测天气、当天实时路况。v1 不用当天值；
  天气用预报，训练时要么用历史预报存档，要么评估“用实测训练、用预报推断”带来的落差。
- **与晚点关系弱、又只能间接用的**：311。见下节。

候选清单和数据集编号见 [data-sources.md](../requirements/data-sources.md) §4。

## 3. 被否决的方案

- **把 311 作为路况代理放进 v1**：次日的 311 拿不到，只能用前一天的除雪类投诉量。
  它反映的是居民感受和报修习惯，与公交晚点之间隔了好几层，作为卖点讲不通，
  作为特征的增益也存疑。除雪状态和停车禁令更直接地描述了道路状况，用它们替代。
  若 v1 评估显示冬季误差有明显缺口，可以再做一次带 311 的对照实验。
- **训练时用实测天气、不处理预报误差**：会高估上线后的准确度。

## 4. 后果

- 需要一份历史天气预报来源，或者在评估里专门量化预报误差的影响。
- 实时数据全部推迟到 v2（[roadmap.md](../roadmap.md)）。
