# 开发文档

面向开发者的需求、决策与设计记录。中文书写，文件名用 English kebab-case。
对外说明在 [../guide/](../guide/)，两者不混放。

## 一、两个性质，一条建目录的规则

文档不按主题分，按性质分。写之前先定性质，落点唯一。

- **常青**：描述现状，原地改写，历史交给 git。
  - [roadmap.md](roadmap.md)：能力阶段
  - [requirements/](requirements/)：要做什么，以及事实依据
- **事件**：描述一次性的事，写完冻结，只追加更正、不改写。
  - [adr/](adr/README.md)：一个决策的取舍
  - [design/](design/README.md)：一次变更打算怎么做
  - `launch/`：一次变更实际怎么上线，第一篇出现时建目录
  - `postmortem/`：造成实际影响的故障复盘，第一篇出现时建目录

**目录只给会增长的东西。** 事件类单调累积，每类一个目录；常青类里只有
`requirements/` 会增长，其余单篇放顶层。

### 判定顺序

自上而下问，第一个“是”就是落点：

1. 系统变了它会不会被改写？会 → 常青（`requirements/` 或顶层单篇）。
2. 记录的是一个以后可能被推翻的决策？→ `adr/`
3. 记录的是一次变更打算怎么做？→ `design/`
4. 记录的是一次变更实际上线的过程和验收？→ `launch/`
5. 记录的是出事后的复盘？→ `postmortem/`
6. 都不是 → 多半不该进本仓库，见下一节。

## 二、不进本仓库的东西

- 改了哪些文件、怎么验证 → PR 描述
- 某一行为什么这么写 → code review
- 这次提交做了什么 → commit message
- 进度、排期、临时阻塞、状态更新 → 仓库外
- 课程、求职、个人日程等只在私人笔记里成立的背景 → 仓库外，且本仓库不引用它们

文档只写三个月后重读仍然有用的内容：问题是什么、方案的取舍、被否决的选项及理由、
约束与假设、验收判据。**文档里不写“✅ 已完成”这类进度标记。**

## 三、必须留下的东西

可读性服务于可追溯性，两者冲突时保留证据。

- **数字带三件套**：测量时间、测量入口（可重跑的命令或查询）、测量环境
  （实时 API、某个文件、某次构建）。缺一件，就无法判断这个数字是否已经失效。
- **失败路径留结论，不留回放**：触发原因、暴露它的观测量、推翻先前归因的证据。
- **判据留命令和关键数字**，不贴终端输出，不写“已验证”。
- **被否决的选项和理由必须留下**，否则下一个人会把同一个方案再提一遍。

## 四、写作规则

- 每篇文档必须被 [../README.md](../README.md) 索引恰好链接一次。
- 宁可合并不要拆分。
- 事件类文档写完冻结。数字或归因被推翻时，在原处追加带日期的更正块
  （`> 🔴 YYYY-MM-DD 更正：…，依据 …`），原文不动；结论变了才另写一篇并标注取代关系。
- 常青文档原地改写，但被推翻的实测数字连同推翻它的证据留在正文，一行注记即可。
