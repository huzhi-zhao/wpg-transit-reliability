# 数据源

> 本篇所有数字均于 **2026-11-24** 对 City of Winnipeg 开放数据门户
> （`data.winnipeg.ca`，Socrata SODA API，实时）和 Winnipeg Transit 公开的 GTFS 测得，
> 命令见各节。上游会变，引用前看测量时间。

## 1. 主数据源：Transit On-Time Performance

门户上有两张表：

- **存档** `cymk-nyei`：每行是一个月度压缩包的元数据（起止日期、行数、大小、下载地址）。
  - 111 个月度文件，2017-07 至 2026-09，**行数合计 625,468,342**。
  - 单月压缩包 80 到 204 MB。
- **最近一期** `gp3k-am4u`：5,130,584 行，覆盖 2026-10-10 至 2026-11-23，
  73 条线路、3,885 个站点。每天更新。

```bash
curl -s "https://data.winnipeg.ca/resource/cymk-nyei.json?\$select=sum(rows),min(start_date),max(end_date)"
curl -s "https://data.winnipeg.ca/resource/gp3k-am4u.json?\$select=min(scheduled_time),max(scheduled_time),count(distinct%20route_number),count(distinct%20stop_number)"
```

### 1.1 字段

存档 CSV 的表头，2017-07 与 2026-09 两个文件一致（读压缩包头部实测）：

- `Row ID`：自增编号
- `Stop Number`：站点编号，对应 GTFS `stop_id`
- `Route Number`：线路编号。改造前是 `15` 这类数字，改造后是 `F7`、`D19` 这类编号
- `Route Name`：线路名
- `Route Destination`：终点方向，可替代方向字段
- `Day Type`：`Weekday` / `Saturday` / `Sunday`
- `Scheduled Time`：计划离站时间，精确到秒，本地时间
- `Deviation`：实际与计划的偏差，单位秒，**负数为晚点，正数为提前**（门户说明原文）
- `Location`：站点坐标，WKT `POINT`

一行 = 一辆车离开一个站点一次。门户说明：数据来自车载计算机和 GPS，
有少量传输缺失和 GPS 错误，按车载上报原样发布。

**没有的字段**：`trip_id`、车辆编号、方向编号、载客量、到站时间。

### 1.2 月度行数的断层

- 2017 至 2020 年：每月约 700 万至 870 万行。
- 2025-04：2,869,689 行（明显偏低，原因未查）。
- 2025-07 起：每月 235 万至 355 万行，约为早年的三分之一。

线路编号在同一时期换了体系，说明 2025 年中有一次线网改造。
行数下降是改造后班次和站点减少，还是采集覆盖缩小，**尚未区分**；
在区分之前，改造前后的准点率不能直接比较。

```bash
curl -s "https://data.winnipeg.ca/resource/cymk-nyei.json?\$select=start_date,rows&\$order=start_date&\$limit=200"
```

## 2. 班次重建：与 GTFS 联结

时刻表：`https://gtfs.winnipegtransit.com/google_transit.zip`，
测量时的 feed 有效期为 2026-09-06 至 2026-12-12。`stop_times.txt` 有 `trip_id`、
`stop_id`、`departure_time`（精确到秒）、`stop_sequence`；`trips.txt` 有
`route_id`、`service_id`、`direction_id`、`block_id`。没有 `timepoint` 字段。
包内附带的 `LICENCE` 是 Open Data Commons PDDL 1.0（公共领域），使用和再发布不受限制（P0 的 I6，源实测，2026-11-24）。

**D19 抽样（2026-11-18，周三）**：

- 当天 D19 存档记录 1,116 行，按（`Stop Number`，`Scheduled Time` 的时分秒）
  对 GTFS 的（`stop_id`，`departure_time`）联结，**全部匹配**。
- 同一键在当天出现重复 3 组（1,116 行，1,113 个不同键），需要清洗。
- D19 工作日（`service_id = 1`）时刻表共 114 班，每班 32 或 33 站。

**窗口 A 全量**（2026-11-24，命令见 §3）：工作日记录 4,574,667 行，
按（站点，计划时间，线路，服务日）联结，恰好匹配一个班次的 99.87%，匹配到多个班次的 0.13%，
没匹配上的 71 行（全部是 211 路）。计划时间过午夜的记录按前一服务日的 24 时以后计。指标实测。

结论：**改造后的记录可以靠时刻表还原 `trip_id` 和站序**。历史各期需要对应时期的 GTFS，
能否拿到是 P0 的检查项。

## 3. 缺班

> 本节数字除特别注明外，均为 **2026-11-24** 对窗口 A 测得：最近一期表 `gp3k-am4u` 的全部
> 5,130,584 行（2026-10-10 至 2026-11-23，逐日行数与 API 的 `count(*)` 一致），
> 联结当时的 GTFS（有效期 2026-09-06 至 2026-12-12）。只看工作日，共 29 个服务日
> （10-12 感恩节、11-11 国殇日按周日班次运行，不计）。全部为指标实测。
> 判据和门槛见 [P0 可行性探针](../design/20261124-feasibility-probe.md)。

```bash
probe/fetch_recent.sh          # 逐日下载到 data/raw/recent/，_counts.tsv 记录核对结果
uv run probe/window_a.py       # 输出本节和 §5 的全部数字，另存 data/out/window_a.json
```

缺失的单位是**整个班次**：出现的班次基本每站都有记录，缺的班次一站都没有。
（最早的读数是 2026-11-18 一天 D19：114 班里 37 班有记录。）

**覆盖率（G1，通过）**

- 全网合并：62.3% 的计划班次至少有一条记录。
- 按线路取工作日覆盖率中位数，72 条线路的分布：P10 48.5%，中位 69.1%，P90 100%。
- 覆盖率中位数 ≥ 30% 且站点完整度中位数 ≥ 90% 的线路有 68 条，门槛是 3 条。
- D19：覆盖率中位数 36.0%，站点完整度 92.6%，工作日 114 班。
- **每天差别大**：全网单日覆盖率最低 45.1%，中位 62.2%，最高 84.0%。

**按时段（G2b，不通过）**

按班次首站发车时间分段的覆盖率：

| 时段 | 覆盖率 | 班次·天 |
|---|---|---|
| 6 时前（不在门槛内） | 68.4% | 9,860 |
| 6–9 时 | 71.7% | 42,949 |
| 9–15 时 | 66.4% | 56,956 |
| 15–18 时 | 65.3% | 43,993 |
| 18 时后 | 36.5% | 32,045 |

四段极差 35.2 个百分点，门槛是 15。按小时看，17 时 63%，此后逐时下降：19 时 40%，21 时 28%，23 时 15%。
分线路看，白天减晚间的覆盖率差：P10 −2 个百分点，中位 11，P90 39；没有一条线路晚间覆盖率低于 10%。
全网合并的落差大于单条线路的中位落差，说明晚间班次多的线路本身覆盖率也低。

**缺失按车次链成片（G2c，只记录）**

同一 `block_id` 当天有 2 个以上班次的 21,112 个“车次链·天”里，96.2% 是整条都有或整条都缺；
如果各班次独立缺失，按当天覆盖率算只该有 19.5%。缺失跟着车次链走，也就是跟着车辆走，
最可能的解释是部分车辆没有上报。

**G2b 不通过之后补的两项检查（只记录，结果出来之前没有改任何门槛）**

- **晚间落差来自哪些车在跑。** 同一车次链当天白天班次全部有记录的，它晚上的班次也基本有记录：
  按发车小时，18 时 99%，19 时 98%，21 时 94%，23 时 83%，过午夜约 80%。
  而跨到晚间的车次链，白天部分的覆盖率本身就只有 58.6%；只跑白天的车次链是 79.6%。
  也就是说，会上报的车到了晚上仍然上报，晚间缺得多主要是因为跑晚间的车次链更少是会上报的车；
  过了 22 时另有一段较小的、随时间增长的缺失。
- **缺失和晚点没有可见的关系。** 只看 18 时前发车的班次，以“线路·天”为单位（2,041 个），
  看覆盖率高的日子里被记下来的班次是否更晚点。如果晚点的车更容易缺记录，两者应正相关。
  扣除线路和日期的平均水平之后，覆盖率每高 10 个百分点，晚点超过 300 秒的比例只变化 +0.02 个百分点
  （按天自助法 95% 区间 −0.14 到 +0.18）；只扣线路时是 +0.06（−0.24 到 +0.32）。
  同一线路内覆盖率的标准差有 18.7 个百分点，变化幅度足够看出关系。
- **仍然测不了的**：不上报的车如果在车型、车龄上和上报的车不同，而车型本身影响晚点，
  留下来的样本仍会有偏。数据里没有车辆编号，这一点只能写成局限。

**范围调整**：MVP 只做首站 18:00 前发车的班次，见 [ADR 0004](../adr/0004-mvp-trips-departing-before-1800.md)。
这一范围内四个时段（6 时前、6–9、9–15、15–18 时）覆盖率在 65.3% 到 71.7% 之间，极差 6.4 个百分点。
这个范围是看到结果之后划的，不能当作 G2b 通过。

**数据质量（I1）**

- 同一（站点，线路，计划时间）的重复记录：22,465 行，0.44%。联结时保留 `row_id` 最小的一条。
- 偏差绝对值超过 3,600 秒：7,345 行，0.14%。
- 坐标缺失或落在城市范围外：0。

准入规则：只用前一天已知的信息（[ADR 0003](../adr/0003-features-known-the-day-before.md)）。
“行数”列为 2026-11-24 的 `count(*)`；未写行数的尚未测。

**MVP 候选**

- **天气**：降雪量、冻雨、极寒、大雨。ECCC 日数据在温尼伯一带没有降雪量字段，
  降雪改用 Open-Meteo（历史用 archive API，2025-07-01 至 2026-11-23 的日降雪量全部有值，
  2026-11-24 测；前一天的预报用 historical-forecast API）。气温仍可用 ECCC 观测。
  训练用的历史值和预测时的预报值之间的差距需要处理。命令见

- **冬季道路运营**：除雪状态（逐地址）`g3p4-h83y`、停车禁令 `mfzv-893p`。

- **客流（停站时间的代理）**：分站点上下车人数 `bv6q-du26`，2,405,173 行，

- **铁路平交道口**：班次下游的平交道口数量，固定特征。道口位置来自 Transport Canada
  的道口清单（未测）；火车时刻不公开。
- **河水位和春汛封路** `tgrf-v2zc`：沿河道路的季节性封闭。

**实时修正阶段才用（次日拿不到）**

- 实时路段流量和车速 `bh78-7qpb`：1,465,467 行，2026-05-21 起，20 个站点，每 15 分钟。
- 固定计数站 `46sc-6jrs`：1,880,523 行，2019-12 起。MVP 只能用历史典型值。

**不采用**

- 311 服务请求：次日拿不到，只能用前一天的投诉量间接代表路况，与晚点的关系弱。
  见 [ADR 0003](../adr/0003-features-known-the-day-before.md)。

**拿不到**

- 取消班次、车辆故障、缺司机等运营内部信息：不公开。

## 5. 信号强度和标签效度（P0 的 I2、I3）

窗口 A，测量方式同 §3。事件为“晚点超过 300 秒”，全部观测中的发生率是 11.6%。指标实测。

**班次之间拉得开（I2 班次间差异）**

- 观测满 10 天的（班次，站点）单元有 195,360 个。发生率 P10 0%，中位 4.5%，P90 35.0%。
  如果每个单元的真实发生率都一样，只靠抽样噪声，同样的分位数应是 4.0%、11.1%、20.8%。
  实际分布比噪声宽得多，单元之间的差别是真的。
- 方差分解：以“一个班次在一天”为单位，取它各站晚点超过 300 秒的比例，
  用 Henderson 方法 I（矩估计，交叉随机效应）分成三部分。设计文档举例的 logistic 混合模型
  用 statsmodels 跑 25 万行十分钟没有收敛，改用这个方法。

  | 来源 | 标准差 | 方差占比 |
  |---|---|---|
  | 哪一班（班次） | 0.144 | 31.3% |
  | 哪一天（日期） | 0.023 | 0.8% |
  | 这一班在这一天（交互项和站点噪声） | 0.212 | 67.9% |

  窗口 A 是秋季，日期这一项小是预期之中；冬季的日期效应要看窗口 B。

**标签效度（I3）**

- 终点站的观测占 2.36%。
- 当前 GTFS 的 `arrival_time` 和 `departure_time` 在所有行上都相同，计划停站时长无法从 GTFS 得到，
  “停站 ≥ 2 分钟”这一半测不了。
